What it does

SpaceOooops is a game about the trade-offs of space mission design. One Mission has four steps: Design → Launch Review → Run → Debrief.

  1. Choose how to play: solo, or a team of 2 to 4 players on one screen.
  2. Pick a Scenario and read its brief: the objective, the Science Value required, the minimum Lifetime and the Budget. There are seven Scenarios. Three are set in Angola, home of the challenge author: Crop Watch (easy), Connect the Villages (medium) and Space Weather Sentinel (hard). Four more are set in countries of Space Apps partner agencies: Amazon Watch (Brazil), Glacier Watch (Argentina), Cyclone Watch (India) and Disaster Response (Japan).
  3. Design the mission in four Role tabs:
    • Science: 9 Instruments, each with its own Mass, Power, cost, Data and fit to the Scenario.
    • Spacecraft: structure from a CubeSat 3U to a 100 kg SmallSat, solar panels, battery, attitude control and onboard computer, each in a Basic or Flight-proven reliability tier.
    • Launch & Orbit: 3 Orbits (400 km low Earth orbit, 600 km sun-synchronous, geostationary) and 6 Launch Vehicle classes.
    • Budget & Comms: UHF, S-band or X-band radio.
    Live gauges show Budget, Mass, Power, Data and Lifetime, and every number has a "why it matters" tip. Easy Scenarios add first-time hints.

[Insert → Inline Image: images/1-design.jpg. A heavy radar turns four gauges red.]

  1. Pass the Launch Review. It blocks a Design that breaks a hard constraint, for example a spacecraft too heavy for its Launch Vehicle, and says why. In team play every Role votes Go or No-Go, and a No-Go shows its objection.

[Insert → Inline Image: images/2-launch-review.jpg. Four broken constraints, each explained.]

  1. Watch the Run: a day-by-day simulation over a 3D orbit animation with live dashboards. Random Events happen along the way. Some pause the Run and ask you to decide: enter safe mode for a solar flare or ride it out, wait out a ground-station outage or buy time on another station, dodge debris or risk it. Some options are gambles with a stated chance. If you skip a question, the spacecraft takes the safe default.

[Insert → Inline Image: images/3-run-solar-flare.jpg. A solar flare wave reaches the spacecraft in safe mode.]

  1. Read the Debrief: success or failure, the Score line by line, the causes in plain language with this Run's numbers, your decisions and their effects, each Role's Personal Objective, a Real-Mission Match and a comparison with your previous Run. Then change the Design and fly again.

[Insert → Inline Image: images/5-debrief.jpg. The Debrief explains why.]

Every Run is saved in the browser's history with a Load this Design button. Share design copies a link that opens the same Scenario and Design in any browser.

How it works

All game rules live in one simulation module written in Rust, with no user-interface code in it. It computes the resource budgets, runs the Launch Review, flies the Run from a seed (the same seed and Design always give the same Run) and builds the Debrief. Every game number sits in plain data files with its source written next to it, and values we tuned for play are marked as game estimates.

The user interface is built with Leptos and compiled to WebAssembly. A low-poly 3D scene (Earth, the spacecraft model built from the chosen parts, the launch, the orbit) is drawn with three.js behind the interface. Without WebGL the game falls back to a static background and stays fully playable. There is no backend: the game is a set of static files on GitHub Pages.

Benefits and intended impact

  • The whole mission at once. Students see every part together, not one topic at a time. Changing one part moves five gauges.
  • No single correct answer. Different combinations of Instruments, Orbits and Launch Vehicles can meet the same objective.
  • The game explains why. The Launch Review and the Debrief give causes and numbers, not only pass or fail.
  • Failure is cheap. A Run takes minutes, and the comparison with the previous Run shows what the change did.
  • Real negotiation in team play. Each Role has a Personal Objective that pulls against the others: Budget & Comms wants to spend under 80% of the Budget while Science wants more Science Value.
  • Links to real missions. The Real-Mission Match connects the player's Design to one of 13 real missions, such as NASA's Dellingr CubeSat, AngoSat-2, Amazonia-1, ALOS-2, SAOCOM and INSAT-3DR.

We hope teachers and space clubs can use it as a 20-minute classroom activity: one shared screen and four students arguing over one spacecraft.

Creativity

  • Three kinds of Random Events: real (each with a short note on how it happens to real missions), lucky (good news) and Unexplained (clearly marked fantasy events, such as a space cat chasing the downlink beam or aliens borrowing the satellite). The jokes keep players reading the event log, where the real engineering lessons are.
  • Go/No-Go vote and Personal Objectives turn a single-player optimisation puzzle into a team discussion.
  • The 3D spacecraft is built from the parts the player picked, and a failed Mission ends with a matching fate: tumbling, dark, re-entry or adrift.

Factors we considered

  • Access and cost: free, runs in a browser, no install, no account, no server. Nothing is sent anywhere; history stays in the browser.
  • Low-end devices: Low/High Graphics and Full/Reduced Motion settings, a non-WebGL fallback, and layouts tested at phone width.
  • Readability: body text uses Atkinson Hyperlegible, a typeface designed for legibility. Concepts are explained in simple terms inside the game, with a glossary of terms used the same way on every screen.
  • Honesty about numbers: the in-game Sources page lists where values come from and says which are primary sources, secondary sources or game estimates.
  • Energy: static hosting and client-side simulation, so no servers run for the game.

Tools and languages

Rust, WebAssembly, Leptos 0.8, Trunk, JavaScript, three.js 0.186.1, CSS, TOML data files, Playwright browser tests, GitHub Actions and GitHub Pages. The simulation is covered by native Rust tests, and the release build is checked by browser tests before every deploy.
